### 我的理解

- **只改缺陷（bug）角色。** 执行记录列序不动，按原样保留。
- 用户**自己手动拖列**，不需要走「重建」。
- 我改的是**默认建表逻辑**：`backend/app/lark/provision.py` 里 `BUG_SCHEMA` 的字典顺序。
  改完之后这些路径自动跟随，无需逐处修改：
  `schema_order("bug")` → `table_fields()`（建新表）/ `provision_plan()`（补表头）/
  `retype_plan()`（改类型）/ `layout_matches()`（判断表头是否合格）/ `_planned_field()`。
- `REQUIRED_BUG_FIELD_TYPES`（校验必填列存在性与类型）**不用改**，它不关心顺序。

### 已实测的证据

| 结论 | 证据 |
|------|------|
| Lark 按我们发送的 fields 顺序建列，第一列即主列 | 用工具当前 `table_fields("bug")` 建探针表，读回顺序与发送顺序完全一致、`问题描述` 是 `★主列`；探针表已删除 |
| 改列序**不会**让已确认的目标失效 | `schema_fingerprint()` 用的是 `sorted(types)`（`fields.py:122`），顺序变化不改变 fingerprint |
| 当前仓库 HEAD 建表已经会带上 fields | `provision.py:711` 与 `:851` 都传 `table_fields(role)`；产出 8 列、`问题描述` 主列 |

### ⚠️ 需要你知道的两个副作用

1. **`layout_matches()` 是顺序敏感的**（`provision.py:607` 逐列比名字）。改完 `BUG_SCHEMA` 后，在**你拖动列序之前**，线上缺陷记录会被判定为"表头不合格"，「重建」按钮会提示表头不对。你拖完就一致了。
2. **补表头只能追加到末尾。** 如果某张已有表缺某一列、走「设置表头」补，新列会落在**最后一列**，不会插进模板顺序的位置。缺列的表补完仍需要手动拖。新表不受影响。

## 2. 需求 R2 — 执行记录的负责人/报告人改成人员列

### 我的理解

- 执行记录 `负责人` / `报告人` 现在是**文本列**，要改成**人员列**。
- **负责人留空没关系**（后面指派给领导）；用户说"如果要值我会说"。
- 我改：`RUN_SCHEMA` 里 `负责人` / `报告人` 从 `FieldSpec(1)` 改成 `FieldSpec(11, PERSON_PROPERTY)`，这样**以后新建的执行表默认就是人员列**。
- 你手动改列类型那一步：**改完必须在页面上重新「读取表格 + 确认本组写入目标」**。

### ⚠️ 这是最容易踩的坑（必须说清楚）

`person_field_names(target.schema_fingerprint, "execution")` 决定写端按不按人员列处理。

```
改列类型后不重新确认：
  fingerprint 里还是 负责人:1 / 报告人:1（文本）
  → 写端仍把 "Max"、"待指派" 当文本发进人员列
  → Lark 拒绝（人员列只吃 [{"id": "ou_xxx"}]）
  → 整行 create 失败，重试也救不回来，该组所有行卡住
```

### ⚠️ 改列类型的另一个后果

文本值改人员列时，**现有 8 行执行记录的 `负责人="待指派"` / `报告人="Max"` 会丢失**（Lark 不保留文本→人员的转换值）。线上是测试数据，默认按可接受处理。

## 2.5 `multiple` 到底是什么（实测结论）

**它是什么**：飞书多维表格「人员」字段（type 11）的一个属性 `property.multiple`——**一个格子能放几个人**。

| 值 | 在 Lark 界面里 | 对 API 写入 |
|---|---|---|
| `false` | 单元格只能放 1 个人 | **不拒绝**多个 id，**静默只保留第一个** |
| `true` | 可以不断「＋」加人 | 全部保留 |

**这是纯 UI 开关，不是 API 约束。** 探针实测（一次性的表，验完即删）：

```
多人列 multiple=true  ← 写 2 个 id → 落库 2 个：['Max Wang', '于小宁']        ✓
单人列 multiple=false ← 写 2 个 id → 请求返回 code 0 且回显 2 个，
                                    实际只落库第 1 个：['Max Wang']          ← 静默截断
单人列/多人列         ← 写 1 个 id → 都正常落库                              ✓
```

**对我们的结论**：写端 `_person_field_value()` 每个人员列**永远只发 1 个 id**（`[{"id": open_id}]`），
所以 `multiple` 取 `true` 还是 `false`，**对自动写入完全没有差别**。选 `true` 的唯一实际收益是：
你在 Lark 里手动编辑时可以在一个格子里挂多个人；自动写入不受影响，也不花任何成本。

**⚠️ 连带挖到的真坑**：`create` 记录的**响应是你请求体的回显，不是落库快照**——上面单人列明明被截断了，
响应里却照样回了 2 个 id 且 `code 0`。**任何"写后校验"都必须再 GET 一次记录**，拿响应当落库证据是错的。

## 3. 需求 R3 — 页面可配置人员 open_id

### 原话

> 这个问题，要允许我页面设置界面给配置 `DEFAULT_REPORTER_ID` 或者把缺陷表的哪个拿来，因为两侧是一致的。
> 我希望 **报告人 和 负责人** 给我留个写 id 的地方，我在页面可以设置。

### 我的理解

- 页面上要有 **两个输入框**：`报告人 open_id`、`负责人 open_id`。
- **报告人一处的配置，同时喂给两侧**：执行记录.`报告人` 和 缺陷记录.`反馈人`（"两侧是一致的"）。
  即：不是两个独立配置，而是 **1 个「报告人/反馈人」共用项 + 1 个独立的「负责人」项**。
- 负责人留空 → 执行记录.`负责人` 整列不发（保持空），不报错、不阻塞整行。

### 现状与改动点

```
现在: worker.py 只读环境变量
        reporter_id = settings.default_reporter_id     → 只喂 缺陷.反馈人 + 执行.报告人
        负责人                                       → 根本没有 id 可用（写端连参数都没有）
        证据: write.py  "负责人": _person_field_value("负责人", text=owner, person_fields=people)
                                                          ^^^^^^^^^^^^^^^^^^^^^ 没有 open_id 参数

改后: 页面写入 → 数据库 → worker 读取 → execution_fields 传 owner_id/reporter_id
```

### 实现范围（我的判断）

| 项 | 内容 |
|---|---|
| DB | 现在**没有任何配置表**（`models.py` 14 张表里没有）。需新增一张（如 `app_settings` 单行表）+ 迁移 `0015` |
| API | `GET/PUT /api/settings/lark-people`（写操作走 admin + CSRF） |
| 代码 | `config.py`（env 变成初值/兜底）、`write.py`（`execution_fields` 接 `owner_id`）、`worker.py`（改从 DB 读）、前端新增设置区 |
| 权限 | open_id 是租户内标识、不是密钥，落库可接受 |
| 反作弊 | 改配置**不应**让已确认的目标失效——人员列判定靠 `schema_fingerprint`，与 id 无关 ✓ |
